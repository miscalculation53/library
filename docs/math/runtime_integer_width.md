## 概要

入力の型より値が小さい場合に、計算幅を入口で切り替える。`floor_sum` と `min_of_mod_of_linear` では、正規化後の添字と法がともに $2^{32}-1$ 以下なら、積と除算を `ull` で行う。答えの型と、その型に対する剰余の仕様は保つ。

2026-09-30 に、多倍長整数と整数の演算、整数方程式、最短ベクトル、CRT、小さい法の `static_modint64` にも適用した。追加分の比較と条件は後半にまとめる。

判定は数回の比較で済む。一方、切り替え先の演算や前計算の費用も実行時間に影響するため、複数の方法を実測して選んだ。

## 使用例

呼び出し方は同じ。係数は先に正規化するため、係数だけが大きい場合も小さい計算幅を使える。

```cpp
#include "math/mod_of_linear/floor_sum.hpp"
#include "math/mod_of_linear/min_of_mod_of_linear.hpp"

ll n = 1000000000, m = 1000000007;
auto sum = floor_sum<ull>(n, m, 123456789LL, -987654321LL);
auto minimum = min_of_mod_of_linear(n, m, 123456789LL, -987654321LL);
```

比較の再実行はリポジトリのルートで行う。

```sh
g++-15 -std=c++17 -O2 -DNDEBUG -I . benchmarks/floor_sum_width.cpp -o /tmp/floor_sum_width_bench
/tmp/floor_sum_width_bench > benchmarks/floor_sum_width.csv
g++-15 -std=c++17 -O2 -DNDEBUG -I . benchmarks/linear_mod_width.cpp -o /tmp/linear_mod_width_bench
/tmp/linear_mod_width_bench > benchmarks/linear_mod_width.csv
g++-15 -std=c++17 -O2 -DNDEBUG -I . benchmarks/crt_mod_width.cpp -o /tmp/crt_mod_width_bench
/tmp/crt_mod_width_bench > benchmarks/crt_mod_width.csv
```

## 詳細なドキュメント

#### 計算幅の選択

`floor_sum` は正規化後に $0\le a,b<m$ となり、$an+b\le(m-1)(n+1)$。$n,m\le2^{32}-1$ なら、この値は `ull` に収まる。反復中に $n,m$ は増えないため、累積和の入口で 1 回判定すればよい。区間版は両端の累積和をそれぞれ計算する。

比較した方法は次のとおり。

| CSV の名前 | 方法 |
| --- | --- |
| `wide` | 入力の型に応じて積を拡張する従来法 |
| `entry32` | 入口で小さい値なら、変数を `uint` にして計算 |
| `loop32` | 反復ごとに判定し、値が小さくなった時点で `uint` に切り替え |
| `product64` | 反復ごとに積を `u128` で作り、収まれば 64 bit で除算 |
| `entry_product64` | 入口で判定し、小さい値なら `ull` の変数と積で計算 |
| `entry_bound64` | 入口で $(m-1)(n+1)$ を調べ、64 bit に収まる場合に切り替え |
| `library` | 採用版。`entry_product64` を基本とし、入力が `uint` の場合も同じループを使う |

採用版は、最後の $an+b<m$ で除算前に終了する。正規化後の $a=0$ も即座に終了する。入力が `u128` でも $n,m$ が 64 bit に収まれば、従来の 64 bit 入力用の計算に切り替える。

#### 測定条件

- 2026-09-24、macOS の arm64 ホスト上で x86_64 実行ファイルを実行。GCC 15.2.0、`-O2 -DNDEBUG`。
- `floor_sum` と `min_of_mod_of_linear` は順番を入れ替えた 7 回、CRT は 9 回の中央値。入力生成を除き、呼び出し時の判定と前計算は含める。
- 乱数 seed は `20260925`。各入力で従来法との一致を確認してから測定。
- 通常の `floor_sum` は入力・答えともに `ull`。`min_of_mod_of_linear` は入力・答えともに `ll` で、負の係数も含む。
- 計測中は別のビルドやテストを並走させていない。絶対時間や細かな差は環境に依存する。

#### CRT の初回調査（2026-09-24）

初回の調査では `crt_mod` は元の実装を保った。法が `ll` に格納されている場合について、最初に法を調べ、すべて $2^{31}-1$ 以下なら小さい計算幅に切り替える候補を比較した。

最初に試した「小さい法なら常に Barrett reduction」の方法は、2 本で 5.233 → 8.483 ms、8 本で 24.125 → 25.711 ms、32 本で 43.896 → 28.028 ms。式が少ないと前計算と配列の確保が効いた。

次に、16 本未満では `ull` の積と通常の剰余を使い、16 本以上では Barrett reduction を使う候補を測った。法は $10^9$ 付近または $10^{12}$ 付近の相異なる素数、答えは `modint998244353`。単位 ms。

#### 追加分の切り替え条件

| 対象 | 64 bit に切り替える条件と中間値の上限 |
| --- | --- |
| `BigInteger` と整数の `+ - * / %` | 整数の絶対値を $v$、内部基数を $B$ とし、$v\le\lfloor(2^{64}-1)/B\rfloor$。乗算の繰り上がりと除算の余りは $v$ 未満なので、次の桁の計算は $Bv$ 未満。加算の $v+B-1$ も `ull` に収まる |
| `quadratic_equation_integer` | 係数がすべて $[-2^{30},2^{30})$。判別式の絶対値は $5\cdot2^{60}$ 以下で、根の分子・分母も `ll` に収まる |
| `linear_equations_integer` | 係数がすべて $[-2^{31},2^{31})$。行列式の絶対値は $2^{63}-2^{31}$ 以下。拡張ユークリッド互除法で得た係数と右辺の積も $2^{62}$ 以下 |
| `svp2d` | 成分がすべて $[-2^{30},2^{30})$。基底を縮める間にノルムは増えず、ノルムの二乗・内積の絶対値は $2^{61}$ 以下。丸め除算の $2\cdot\mathrm{dot}+\mathrm{norm}^2$ も `ll` に収まる |
| `static_modint64<M>` | $M\le2^{32}-1$。剰余同士の積は `ull` に収まるため、コンパイル時に計算型を選ぶ |
| `crt_mod_constexpr` | 法がすべて $2^{31}-1$ 以下。正規化された剰余と法を `int` に移し、中間値は `ll` にする |

方程式と最短ベクトルでは、`U=i128` かつ入力が 64 bit 以下の符号付き整数型の場合に適用する。符号付きの下限を安全に扱うため、符号なし型へ変換して定数を加え、まとめて範囲判定する。答えの型、解の順番、最短ベクトルの符号の選び方は従来と同じ。

#### CRT の再調査（2026-09-30）

`crt_mod` は法を `ll` に格納した場合、4 本以上で法の範囲を調べる。すべて $2^{31}-1$ 以下なら、4〜15 本は `ull` の積・剰余、16 本以上は既存の Barrett reduction を使う。式が少ない場合も、剰余を先に正規化することで差の計算を `ll` で処理できる。

Barrett reduction 自体では積の上位 bit を得るために `u128` を使う。改善の中心は、各反復の 128 bit の除算・剰余を減らすことにある。

| 法・式の本数 | GCC 従来 | GCC 採用 | Clang 従来 | Clang 採用 |
| --- | ---: | ---: | ---: | ---: |
| 31 bit・2 本 | 5.346 | 5.252 | 5.943 | 5.947 |
| 31 bit・4 本 | 8.366 | 7.262 | 11.090 | 9.347 |
| 31 bit・8 本 | 25.154 | 20.862 | 38.088 | 30.210 |
| 31 bit・16 本 | 76.154 | 57.598 | 124.457 | 88.567 |
| 31 bit・32 本 | 43.522 | 28.316 | 82.983 | 51.275 |
| 40 bit・2 本 | 11.122 | 10.586 | 10.483 | 10.373 |
| 40 bit・16 本 | 922.803 | 936.742 | 976.603 | 976.305 |
| 40 bit・32 本 | 823.615 | 823.424 | 819.846 | 818.526 |

単位 ms。各条件の入力生成・回数は初回と同じで、順番を入れ替えた 9 回の中央値。`wide` は初回の比較元、`candidate` は初回候補、`library` は採用版。

[比較コード](../../benchmarks/crt_mod_width.cpp)、[GCC 全計測値](../../benchmarks/crt_mod_width_current.csv)、[Clang 全計測値](../../benchmarks/crt_mod_width_native.csv)。再実行時は冒頭の CRT のコマンドで出力先を変更し、Clang ではコンパイラを `clang++` に置き換える。

境界検証で見つかった剰余正規化も修正した。`crt_mod` は先に `%` で剰余を取り、負の場合に法を加えてから差を計算する。これで `LLONG_MIN` の剰余も扱える。`crt_mod_constexpr` は `safemod<T>` を明示し、大きい法で商と法を掛ける部分も拡張型にそろえた。

#### 切り替えを採用しなかった演算

- `Rational<ll>` の有限値の比較：小さい値 100 万回で、GCC は 0.768 → 1.308 ms、Clang は 0.904 → 1.259 ms。範囲判定の費用が積の短縮を上回った。
- CHT・Li Chao Tree で使う `ax+b` の評価：同じ規模で、GCC は 0.632 → 0.673 ms、Clang は 0.764 → 0.958 ms。返り値を `i128` に保った評価部分の比較。データ構造全体の計測ではない。
- `BigInteger::add_term` / `sub_term`：初回の候補では、600 桁・小さい係数でも Clang で約 2〜3% 遅くなり、大きい係数では約 4〜6% 遅くなった。両メソッドは従来の実装を保った。最終 CSV のこれらの行は、変更のない処理の比較になる。

#### 検証

小さい入力の全探索、多倍長整数との比較、負の係数・負の添字、signed と unsigned の混在、32 / 64 / 128 bit の境界を確認した。`floor_sum` の整数の答えは各型のビット幅で合同となり、`modint` と `BigInteger` の答えも一致する。C++17・C++20 の検証で符号付きオーバーフローの検出も有効にしている。

追加分は [境界テスト](../../verify/mytest/ai/runtime_integer_width.test.cpp) で、切り替え前後・負数・`LLONG_MIN`・`ULLONG_MAX`・0 を確認した。多倍長整数は基数 10・16・2、Boost `cpp_int` との照合を含む。最短ベクトルは 128 bit の経路と照合し、CRT は各合同式・解の範囲・法の積を独立に確認する。GCC の C++17、Clang の C++20 と AddressSanitizer／UndefinedBehaviorSanitizer が通過。既存の多倍長整数、二次方程式、二元一次方程式、最短ベクトル、modint64 のテストも通過した。
