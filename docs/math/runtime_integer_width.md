## 概要

入力の型より値が小さい場合に、計算幅を入口で切り替える。`floor_sum` と `min_of_mod_of_linear` では、正規化後の添字と法がともに $2^{32}-1$ 以下なら、積と除算を `ull` で行う。答えの型と、その型に対する剰余の仕様は保つ。

判定は数回の比較で済む。一方、切り替え先の演算や前計算の費用も実行時間に影響するため、複数の方法を実測して選んだ。

## 使用例

呼び出し方は同じ。係数は先に正規化するため、係数だけが大きい場合も小さい計算幅を使える。

```cpp
#include "math/mod_of_linear/floor_sum.hpp"
#include "math/mod_of_linear/min_of_mod_of_linear.hpp"

ll n = 1000000000, m = 1000000007;
auto sum = floor_sum<ull>(n, m, 123456789LL, -987654321LL);
auto minimum = min_of_mod_of_linear(n, m, 123456789LL, -987654321LL);
```

比較の再実行はリポジトリのルートで行う。

```sh
g++-15 -std=c++17 -O2 -DNDEBUG -I . benchmarks/floor_sum_width.cpp -o /tmp/floor_sum_width_bench
/tmp/floor_sum_width_bench > benchmarks/floor_sum_width.csv
g++-15 -std=c++17 -O2 -DNDEBUG -I . benchmarks/linear_mod_width.cpp -o /tmp/linear_mod_width_bench
/tmp/linear_mod_width_bench > benchmarks/linear_mod_width.csv
g++-15 -std=c++17 -O2 -DNDEBUG -I . benchmarks/crt_mod_width.cpp -o /tmp/crt_mod_width_bench
/tmp/crt_mod_width_bench > benchmarks/crt_mod_width.csv
```

## 詳細なドキュメント

#### 計算幅の選択

`floor_sum` は正規化後に $0\le a,b<m$ となり、$an+b\le(m-1)(n+1)$。$n,m\le2^{32}-1$ なら、この値は `ull` に収まる。反復中に $n,m$ は増えないため、累積和の入口で 1 回判定すればよい。区間版は両端の累積和をそれぞれ計算する。

比較した方法は次のとおり。

| CSV の名前 | 方法 |
| --- | --- |
| `wide` | 入力の型に応じて積を拡張する従来法 |
| `entry32` | 入口で小さい値なら、変数を `uint` にして計算 |
| `loop32` | 反復ごとに判定し、値が小さくなった時点で `uint` に切り替え |
| `product64` | 反復ごとに積を `u128` で作り、収まれば 64 bit で除算 |
| `entry_product64` | 入口で判定し、小さい値なら `ull` の変数と積で計算 |
| `entry_bound64` | 入口で $(m-1)(n+1)$ を調べ、64 bit に収まる場合に切り替え |
| `library` | 採用版。`entry_product64` を基本とし、入力が `uint` の場合も同じループを使う |

採用版は、最後の $an+b<m$ で除算前に終了する。正規化後の $a=0$ も即座に終了する。入力が `u128` でも $n,m$ が 64 bit に収まれば、従来の 64 bit 入力用の計算に切り替える。

#### 測定条件

- 2026-09-24、macOS の arm64 ホスト上で x86_64 実行ファイルを実行。GCC 15.2.0、`-O2 -DNDEBUG`。
- `floor_sum` と `min_of_mod_of_linear` は順番を入れ替えた 7 回、CRT は 9 回の中央値。入力生成を除き、呼び出し時の判定と前計算は含める。
- 乱数 seed は `20260925`。各入力で従来法との一致を確認してから測定。
- 通常の `floor_sum` は入力・答えともに `ull`。`min_of_mod_of_linear` は入力・答えともに `ll` で、負の係数も含む。
- 計測中は別のビルドやテストを並走させていない。絶対時間や細かな差は環境に依存する。

#### floor_sum の結果

各行 10 万回、単位 ms。「31 bit」は各値が $[0,2^{31})$、「32 bit」は $[0,2^{32})$ の乱数で、法を正の奇数とする。

| 入力 | 従来 | 採用版 |
| --- | ---: | ---: |
| 31 bit の値を `ull` に格納 | 18.878 | 15.618 |
| 32 bit の値を `ull` に格納 | 17.974 | 16.095 |
| 31 bit の値を `uint` に格納 | 17.835 | 15.542 |
| 31 bit の値を `u128` に格納 | 193.478 | 16.539 |
| 31 bit の値、答えは `u128` | 17.175 | 16.350 |
| 63 bit の値 | 198.254 | 196.450 |
| 64 bit の値 | 205.898 | 202.974 |
| 31 bit と 63 bit を交互に入力 | 109.648 | 107.035 |
| 添字だけ 64 bit、法は 31 bit | 98.009 | 98.636 |
| 係数だけ 64 bit、添字と法は 31 bit | 17.383 | 15.598 |
| 長さ 0 または 1、法 1 | 0.447 | 0.280 |

`uint` への単純な縮小は、32 bit の値で 18.432 ms。`ull` のまま積を小さく保つ方法のほうが速かった。大きい入力での差はおおむね 1〜2% 程度で、添字だけが大きいケースでは約 0.6% 増えている。

[全計測値](../../benchmarks/floor_sum_width.csv)、[比較コード](../../benchmarks/floor_sum_width.cpp)。

#### CRT の調査結果

`crt_mod` は元の実装を保った。法が `ll` に格納されている場合について、最初に法を調べ、すべて $2^{31}-1$ 以下なら小さい計算幅に切り替える候補を比較した。

最初に試した「小さい法なら常に Barrett reduction」の方法は、2 本で 5.233 → 8.483 ms、8 本で 24.125 → 25.711 ms、32 本で 43.896 → 28.028 ms。式が少ないと前計算と配列の確保が効いた。

次に、16 本未満では `ull` の積と通常の剰余を使い、16 本以上では Barrett reduction を使う候補を測った。法は $10^9$ 付近または $10^{12}$ 付近の相異なる素数、答えは `modint998244353`。単位 ms。

| 法・式の本数 | 呼び出し回数 | 従来 | 候補 |
| --- | ---: | ---: | ---: |
| 31 bit・2 本 | 50000 | 5.710 | 6.068 |
| 31 bit・4 本 | 50000 | 8.360 | 7.419 |
| 31 bit・8 本 | 50000 | 24.929 | 20.858 |
| 31 bit・16 本 | 50000 | 74.156 | 55.855 |
| 31 bit・32 本 | 10000 | 42.762 | 27.441 |
| 40 bit・2 本 | 50000 | 11.139 | 11.169 |
| 40 bit・32 本 | 10000 | 821.453 | 819.752 |

4 本以上には効果がある一方、2 本のケースで約 6% 遅くなったため、本体への適用は見送った。[比較コード](../../benchmarks/crt_mod_width.cpp)、[候補の実装](../../benchmarks/detail/crt_mod_width_candidate.hpp)、[全計測値](../../benchmarks/crt_mod_width.csv)を残している。

#### 他のライブラリの調査

| 対象 | 確認したこと |
| --- | --- |
| `count_mod_of_linear` | `floor_sum` を 2 回使うため、今回の改善がそのまま適用される |
| `split_linear_mod` / `LinearModArithmetic` | 既に `ll` の加算と折り返しで処理している |
| 素数判定・素因数分解 | 既に `n <= INT_MAX` で 32 bit の modint に切り替えている |
| `Rational` の比較、CHT・Li Chao Tree の評価 | 数回の積が中心。各演算への範囲判定は効果が小さいと考え、今回は既存の計算幅を保つ |
| 二次方程式・二元一次方程式・`svp2d` | 候補。判別式・行列式・内積など、入力より大きくなる中間値の範囲に応じた判定が必要 |
| `BigInteger` の整数との乗除算・剰余 | 候補。桁のループを持つため、整数の値と内部基数から計算幅を選べる。今回は未測定 |
| Barrett / Montgomery reduction | 積の上位ビットを得るための `u128`。剰余演算を減らす目的に沿って既存の処理を保つ |

#### 検証

小さい入力の全探索、多倍長整数との比較、負の係数・負の添字、signed と unsigned の混在、32 / 64 / 128 bit の境界を確認した。`floor_sum` の整数の答えは各型のビット幅で合同となり、`modint` と `BigInteger` の答えも一致する。C++17・C++20 の検証で符号付きオーバーフローの検出も有効にしている。
