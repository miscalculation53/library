## 概要

[FlatDvec](flat_dvec.md) の一次元化と、次元の長さによる配置選択を比較した計測。
短い次元を連続側に置く配置は、通常のナップサックで約 4 倍遅くなった。
既定の配置には、ループで最後の添字を内側に進めやすい通常配置が適している。
この結果を受け、`FlatDvec` は通常配置を採用した。長さ基準の方式は比較用コードに残している。

一次元化は、小さな vector が大量にできる 3 次元 DP の初期化に効果があった。
配置の自動選択と一次元化は、別々に評価する必要がある。

## 使用例

リポジトリのルートで実行する。

```sh
g++-15 -std=c++17 -Wall -Wextra -O2 -DNDEBUG -I . tools/bench_flat_dvec.cpp -o /tmp/bench_flat_dvec
/tmp/bench_flat_dvec 9 20261005
/tmp/bench_flat_dvec 9 20261006
```

## 詳細なドキュメント

### 条件

- 計測日：2026-10-05。Apple M3 Pro、18 GB、macOS 26.5.2。
- GCC 15.2：`x86_64-apple-darwin25`、Rosetta 経由。Apple Clang 21：`arm64`、ネイティブ実行。
- 両方とも C++17、`-O2 -DNDEBUG`。Clang では一時的な `bits/stdc++.h` に標準ヘッダを列挙し、libc++ でビルドした。
- 各入力・配置で 1 回ウォームアップした後、9 回の中央値を使用。配置の実行順は交代する。
- 入力生成と入出力は計測外。全ての次元を保持する DP を用い、ローリング配列への圧縮は行わない。
- 初期化と DP 本体を別々に計測する。「合計」は確保・初期化から DP 完了までで、解放時間を含まない。
- 全方式で同じ添字・ループ順・遷移を使う。通常配置の添字計算も `FlatDvec` と同じ stride の内積にして、配置の違いを比較する。
- `nested` は既存の `dvec`、`row_major` は最後の添字が連続する一次元配列、`small_first` は短い次元を連続側に置く以前の実装。
- 表と CSV は配置選定時の結果。現在の再現用コードは、`row_major` に現行の `FlatDvec` を使う。
- 基本シードは `20261005`。シード `20261006` でも再確認し、傾向は同じだった。以下の表は基本シードの結果。
- 各問題のサンプルと、各計測入力について全方式の答えの一致を確認。LCS は DP による最長長の計算を対象にした。

ナップサックの形状は `{101, 100001}`。通常配置の stride は `{100001, 1}`、長さ基準は `{1, 101}` になる。
内側の容量ループが 101 要素ずつ飛ぶことが、長さ基準の配置で遅くなる原因と考えられる。

長さ基準の配置は、添字を交換した LCS で小幅な改善があった。
区間 DP と 10000 桁の桁 DP は、長さ基準でも配置が通常と同じなので、時間もほぼ同じだった。
40 桁の桁 DP では配置が変わるが、配列が小さく、差はほぼなかった。
同じ配置でもコード生成や計測の揺れによって時間は変わる。

### 一次元化の効果

Apple Clang 21 での結果。単位は ms。

| 入力 | 入れ子 初期化 | 通常一次元 初期化 | 入れ子 合計 | 通常一次元 合計 |
| --- | ---: | ---: | ---: | ---: |
| 枚数制限つき：50 品、容量 10000、10 枚 | 8.142 | 0.201 | 11.657 | 3.856 |
| 桁 DP：10000 桁、余り 100、フラグ 2 | 12.647 | 0.069 | 24.761 | 10.784 |

一次元化は、入れ子の最内側が小さい場合に確保回数を大きく減らす。
DP 本体の速さはコンパイラにも依存し、GCC の桁 DP では入れ子の方が速かった。
これらは手元の生成入力に対する結果で、AtCoder の実行環境での性能や全入力の傾向を保証するものではない。
