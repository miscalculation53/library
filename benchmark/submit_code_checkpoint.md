# cln の最初のサイズ制限到達までの計測

2026-09-10 に、macOS arm64、Python 3.14.4、GCC 15.2.0、C++23 で計測した。

`cleanup_text` の開始から、65,536 B 未満になった候補を
`CheckpointWriter.save` がファイルへ書き終えるまでの時間。
展開処理と Python プロセスの起動時間は含めない。
計測時だけ最初の書き出し後に停止し、通常の `cln` はその後も短縮を続ける。
変更前後には同一の展開済み入力を与え、各条件を順番に 1 回ずつ測定した。

「初回」はコンパイル用キャッシュが空の状態。「再利用」は変更前後で同じ
作成済みキャッシュを使用した状態。OS のファイルキャッシュは消去していない。
測定値はこの環境での参考値であり、実行のたびに変動する。

| 入力 | 展開後 | 初回・変更前 | 初回・変更後 | 再利用・変更前 | 再利用・変更後 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `template/template.cpp` | 74,550 B | 5.022 s | 2.154 s | 2.182 s | 1.187 s |
| `verify/yosupo/convolution.test.cpp` | 93,290 B | 20.476 s | 16.714 s | 19.729 s | 15.211 s |
| `verify/yosupo/fps_exp.test.cpp` | 109,347 B | 30.944 s | 17.727 s | 24.625 s | 16.175 s |

最初に書き出したサイズは、テンプレートが変更前後とも 61,396 B、畳み込みが
59,494 B → 55,286 B、FPS が 59,671 B → 64,894 B だった。
最初の候補を最小にするよりも、制限内の検証済み候補を早く書き出すことを優先している。

## 変更点

- 最初のサイズ制限到達候補の構文確認では、既存の PCH のみを再利用する。
  新しい PCH は後続の繰り返し検証で必要になってから作る。
- 前処理結果に何度も現れる同一パスの解決をまとめ、正規表現の使い回しと
  不要な文字列コピーの削減によって Python 側の処理を短縮する。
- GCC のテンプレート解析結果から、必要なレコード種別だけを読み取る。
- 制限到達前は、既存の未実体化テンプレート候補のうち、名前が宣言にしか
  現れないものについて宣言も本体と一緒に除く。コンパイル・リンクで確認し、
  失敗時は宣言を残す処理へ戻る。
- テンプレートの削除を無名名前空間化より先に行い、短縮前の大きなコードを
  名前空間化の確認だけのためにコンパイル・リンクする待ち時間をなくす。

ソースのインデント・行内空白・元ライブラリへのリンクは従来どおり維持する。
制限未満の中間結果を、制限以上の候補で上書きしない仕組みも維持する。

```sh
python3 -B -m unittest discover -s tools -p test_submit_code.py
```

29 件成功。新規キャッシュ作成の延期と既存キャッシュの再利用、宣言の同時削除、
宣言を残すフォールバックを追加で確認した。既存テストでは、制限到達後の短縮継続、
中間結果の保護、文字列・マクロ・空白の維持、リンクエラーの検出も確認している。

通常の `submit_code.py cleanup` でも FPS の入力を最後まで処理し、
64,894 B の中間結果を書き出した後、43,432 B まで短縮できることを確認した。
この実行の全体時間は約 78.2 秒だった（変更前の全体時間は比較していない）。

GCC 15.2.0・C++23・`-O2` で元コード、中間結果、FPS の最終結果をコンパイルし、
畳み込み 16 ケースと FPS exp 32 ケースを検証した。乱数とゼロ列、NTT を使う長さも
含め、素朴な畳み込み・係数の漸化式による期待値と 128 回の実行すべてが一致した。

## 追加改善: `01_contests/18` の制限超過

同日に、`multiplicative_prefix_sum` を使う `18/main.cpp` と、以前の `cln` を
最後まで実行しても 67,129 B 残る `18/bundle.cpp` で追加改善を確認した。
以下の「改善前」は上記の高速化を適用済みで、今回の削り残し対策を入れる前の状態。
前後に同一の入力を与え、既存のコンパイル用キャッシュを利用して順番に計測した。
計測区間は上記と同じで、今回は最初の書き出し後も最後まで実行した。

| 入力 | 改善前の最終結果 | 改善後の最初の制限到達 | 改善後の最終結果 |
| --- | --- | --- | --- |
| 以前の短縮結果: 67,129 B | 39.83 s / 67,129 B、制限超過 | 2.937 s / 62,205 B | 17.597 s / 61,854 B |
| `main.cpp` を再展開: 151,091 B | 95.138 s / 67,129 B、制限超過 | 11.879 s / 59,530 B | 29.009 s / 42,078 B |

インデント・行内空白を詰める処理は加えていない。
元の `main.cpp` とライブラリの API も変更していない。

### 削り残しと待ち時間の原因

- 型名の出現回数だけでは、自分のコンストラクタや未使用の型エイリアスから
  参照される型を消せなかった。型・型エイリアス・キャプチャのない `constexpr`
  ラムダ間の参照をたどり、外部から参照されないまとまりを除くようにした。
  これだけでサイズ制限を満たせる場合は、重いテンプレート解析より先に
  コンパイル・リンクして書き出す。
- GCC が報告する汎用ラムダの呼び出し演算子を、通常の関数と取り違えていた。
  不正な宣言への置き換えと、その失敗を切り分けるための繰り返し検証を防いだ。
- テンプレートの `requires` 節や属性が削除範囲に入らず、残った断片で
  コンパイルが失敗していた。改行した戻り値型や属性も含めて削除し、属性の
  文字列内の `;` を宣言の終端と取り違えないようにした。

参照解析では、オブジェクトの同時定義、静的メンバの初期化、`friend`、
キャプチャ・即時呼び出しのあるラムダを保守的に扱う。
同じ行の別の宣言や式、文字列中のコード、マクロ中の宣言も巻き込まない。
トークン結合を含むコードでは、名前だけによる参照解析を行わない。

### 追加後の検証

`test_submit_code.py` は 36 件成功。新たな参照解析に加え、上記の保護対象、
制約・属性付きの宣言範囲、通常の関数とラムダの区別、最初の削除候補の
リンク確認を検証した。

GCC 15.2.0・C++23・`-O2` で、再展開した元コード、以前の短縮結果、
既存ファイルの最初の制限到達結果、再展開時の最初の制限到達結果、最終結果の
5 種類をコンパイルした。小さい入力と非対称な入力の 136 ケースは、
最小公倍数の二重和を直接求めた期待値と照合した。
さらに最大 `N = 100,000,000` の 9 ケースで元コードとの一致を確認し、
計 725 回の実行がすべて一致した。

### 今回の変更

- テンプレート候補の抽出を `-fsyntax-only -fdump-lang-raw` で行い、
  この解析用の実行コード生成を省いた。8 入力で、従来方式と得られる
  テンプレート関数の情報が一致することを確認した。
  未使用関数の警告にはコード生成が必要なため、警告取得の方式は維持している。
- GCC 内部のコンストラクタ名 `__ct` などをソース上の名前に直し、
  リンクエラーが示す必要な定義を削除対象から除けるようにした。
- 必要なテンプレートからの呼び出しをたどり、依存する候補もまとめて保持する。
  `n` などの変数名を関数への参照として扱わない。まとめて残すと、残りの
  テンプレート候補を全部削っても制限内に収まらない場合は、コンパイラの
  診断で必要な定義を確認する方式に戻す。
- `namespace std` の特殊化を元のスコープに保ち、その前後を無名名前空間にする。
  CHT＋有理数の入力でも無名名前空間化が通り、GCC の未使用関数検出が働く。

失敗するコンパイラ起動は、SCC で 14 → 1 回、CHT で 8 → 1 回になった。
候補を書き出す前のコンパイル・リンク確認は維持している。

## 2026-09-13: 最小閉路を使う `18` の高速化

現在の `18/main.cpp` を [比較用入力](submit_code_minimum_cycle.cpp) に保存し、
同じ展開済みコード 125,269 B で変更前後を測定した。GCC 15.2.0・C++23、
Python 3.14.4、既存 PCH を使用。展開と初期キャッシュ準備を除く各1回の実測値。

| 指標 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 65,536 B 未満になるまで | 87.432 s | 10.801 s |
| 最初の制限到達サイズ | 64,367 B | 65,529 B |
| 短縮完了まで | 108.083 s | 37.352 s |
| 最終サイズ | 58,610 B | 44,764 B |
| テンプレート削除の検証回数 | 59 | 4 |

短縮候補を作る際の C++ 構文の読み違いが、検証失敗と分割再試行を増やしていた。
次の3点を修正した。

- 戻り値型の `decltype(...)::type` と、コンストラクタの初期化リストの `:` を区別する。
- コンストラクタの `member{...}` を通過し、関数本体の末尾までを削除範囲に含める。
- `requires` 式を含む制約をテンプレート定義と一緒に扱う。本体だけを除く場合は制約も保持する。

回帰テスト45件が成功。元コード・最初の中間結果・最終結果を `-O2` でコンパイルし、
212ケースずつ、計636回の実行が期待値と一致した。有向・無向、自己ループ、平行辺、
閉路なし、非負重み、有向の負辺・負閉路を含む。期待値は別実装の最短路で求めた。
測定の内訳とハッシュは [結果JSON](submit_code_minimum_cycle_results.json) に保存している。

比較用入力の再計測:

```sh
python3 -B benchmark/submit_code_matrix.py --output /tmp/cln-minimum-cycle \
  --cases minimum_cycle --label current
```
