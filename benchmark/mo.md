# Mo's algorithm の定数倍改善

## 適用結果

Mo の前処理に「基数ソート＋共用」を適用した。
基数ソートは [algo/radix_sort.hpp](../algo/radix_sort.hpp) に切り出し、整数キーの安定ソートと添字列の取得に対応させた。
最良候補だけを保持し、`unzip` と順序配列のコピーも省いた。

以下は適用後のコードと保存した変更前のコードを、同じ実行で再測定した結果。
単位は ms、各 5 回の中央値。[mo_applied.csv](mo_applied.csv) に収録した `library` が適用版。

| 入力 | 変更前の前処理 | 適用後の前処理 | 変更前の走査込み | 適用後の走査込み |
| --- | ---: | ---: | ---: | ---: |
| ランダム、$n=q=200000$ | 136.423 | 5.528 | 176.340 | 47.093 |
| ブロック両端、$n=q=200000$ | 133.179 | 5.691 | 155.386 | 29.013 |
| ランダム、$n=200000,q=1000$ | 0.412 | 0.027 | 2.612 | 2.364 |
| ランダム、$n=20000,q=200000$ | 132.187 | 4.618 | 139.620 | 12.023 |

適用版の処理順は、比較用の `radix_bucket6` と一致した。
C++17・C++20 と標準ライブラリの境界チェック付き構成で検証した。
符号付き・符号なしの 8～128 bit 整数、安定性、ムーブ専用の要素、Mo の 3 種類の API、
大きい移動距離、既存の Slider、木上版を確認している。

以下は方式を比較した時点の結果。測定時の負荷により、再測定とは絶対時間に差がある。

## 検討時の結論

**まず、右端のソートを 6 通りの候補で共用する変更を勧める。**
20 万要素・20 万クエリのランダムな区間では、前処理が **176.1 ms → 21.6 ms**、
走査込みが **236.7 ms → 78.7 ms** になった。移動回数はほぼ同じだった。

変更量を小さくするなら、比較キーの事前計算も有効。
こちらは処理順を完全に保ち、前処理が **176.1 ms → 95.0 ms** になった。

比較用コードは [mo.cpp](mo.cpp)、結果は [mo.csv](mo.csv)。
ライブラリには「基数ソート＋共用」を適用した。変更前のコードは [mo_reference.hpp](mo_reference.hpp) に保存している。

## 測定条件

- 2026-09-26、Apple Silicon / macOS、GCC 15.2.0、x86_64 実行ファイル（Rosetta）。
- `-std=c++20 -O2 -DNDEBUG`。クエリの座標は `long long`。
- 基本は $n=q=200000$。$n=200000,q=1000$ と $n=20000,q=200000$ も測定した。
- 配列・木の属性は 4096 種類の値。クエリは区間・パス上の値の種類数を求める。
- ウォームアップ後、方式の実行順を巡回させて各 5 回測定した中央値。
- 入力生成、木の構築、答えの照合は計測外。順序の生成、各方式の配列確保、走査は計測内。
- 配列では `internal::mo_order` または比較用の順序生成と、共通の走査コードを測った。
  `mo` 本体が走査前に行う最後の `unzip` は共通の走査コードには含まれない。
- 木では変更前版に対応する区間変換・走査コードと候補を比較し、変更前の `mo_on_tree` の全出力と照合した。
- 小規模入力は素朴な集計とも照合した。空クエリ・1 頂点・重複クエリも確認した。
- キー方式の順序一致、バケット・基数ソートの整列条件、順列性、Hilbert 順序の一意性・隣接性も検査した。

実時間には環境負荷によるばらつきがある。CSV に最小・最大も収録した。
数 % の差は参考値として扱い、他の CPU・コンパイラや重いコールバックへの効果は別途測定する。

## 変更前実装の主な負荷

[ds/mo/mo.hpp](../ds/mo/mo.hpp) は、ブロック幅 3 通りと半ブロックのずらし 2 通りを試す。

1. 比較のたびに `(l + offset) / b` を計算する。ソートは 6 回行う。
2. 各候補で `unzip` し、左端と右端の配列を作る。通常の `mo` 呼び出し全体では計 8 回になる。
3. 6 本の順序配列を同時に保持し、選んだ配列を返す際にもコピーする。

幅とずらしを試す方針には意味がある。半ブロックずらした候補を加える考え方は、
[noshi91 の解析](https://noshi91.hatenablog.com/entry/2023/04/13/224811)に対応する。
ランダムな区間向けの幅については、[Nyaan の解析](https://nyaannyaan.github.io/library/misc/mo.hpp.html)も参考になる。

## 比較した方法

| CSV の方式名 | 内容 |
| --- | --- |
| `current6` | 変更前の `internal::mo_order` |
| `key6` | `(ブロック番号, 向きを反映した右端)` を 64 bit キーにして 6 回ソート。最良候補を順次保持 |
| `radix6` | 同じキーを 16 bit ずつ基数ソート |
| `bucket6` | 右端で 1 回ソートし、各候補をブロックごとの配列に振り分ける |
| `radix_bucket6` | 右端の 1 回のソートにも基数ソートを使う |
| `key2` | 幅 $n/\sqrt{q+1}$ と、その半ブロックずらしだけを試す |
| `key1` | ランダムな区間向けの幅で 1 回だけソート |
| `key6_local` | `key6` の順序に対し、距離が縮む隣接交換を 1 回走査して適用 |
| `hilbert` | Hilbert 曲線の順序で 1 回ソート |
| `origin6` | `key6` の候補評価に初期位置 `(0,0)` からの距離も含める |

`key6` は変更前版と全クエリの処理順が一致した。
バケット・基数ソートでは、同一ブロック・同一右端のクエリ間の順序が変わる。

### 右端のソートを共用する手順

1. 全クエリを右端の昇順に 1 回並べる。
2. 候補の幅・ずらしについて、各クエリのブロック番号と各ブロックの個数を数える。
3. 累積和から各ブロックの出力範囲を決める。
4. 右端順に走査し、偶数ブロックには前から、奇数ブロックには後ろから書き込む。
5. 移動距離を評価し、最良候補を保持する。

右端の整列は $O(q\log q)$、各候補の生成は $O(q+\text{ブロック数})$。
既存の 6 通りの幅・ずらしを維持しながら、比較ソートの繰り返しを省ける。

## 配列での結果

表は走査込みの中央値、単位は ms。いずれも $n=q=200000$。

| 入力 | 変更前 | キー事前計算 | 右端ソート共用 | 基数ソート＋共用 |
| --- | ---: | ---: | ---: | ---: |
| ランダムな区間 | 236.7 | 151.9 | 78.7 | 67.1 |
| 長さ 100 以下 | 164.6 | 90.0 | 29.7 | 17.1 |
| 8 か所の狭い範囲に集中 | 159.3 | 96.0 | 37.2 | 24.4 |
| 64 種類の区間を繰り返す | 113.0 | 53.1 | 17.9 | 13.2 |
| ブロックの両端に左端を配置 | 202.7 | 116.9 | 52.2 | 38.7 |

ランダムな区間での前処理は、変更前 176.1 ms、キー 95.0 ms、共用 21.6 ms、基数＋共用 9.9 ms。
移動回数はそれぞれ 73,161,333、73,161,333、73,157,297、73,157,445 回だった。

### 要素数とクエリ数が異なる場合

| $(n,q)$、ランダムな区間 | 変更前 | 右端ソート共用 | 基数ソート＋共用 |
| --- | ---: | ---: | ---: |
| $(200000,1000)$ | 2.80 | 2.56 | 2.54 |
| $(20000,200000)$ | 149.9 | 29.2 | 16.4 |

クエリが少ない場合は走査時間が支配的になる。
このとき順序生成の時間は、右端を比較ソートする版で 0.053 ms、基数ソートする版で 0.079 ms だった。
基数ソートを採用するなら、小さい入力では比較ソートを使う余地がある。

## 処理順を変える案の評価

### 候補数の削減

ランダムな区間では `key1` も速いが、入力分布に依存する。
ブロック両端に左端を配置した入力では、変更前の移動回数 36,975,568 回に対し、
`key1` は 91,083,813 回で **2.46 倍**、`key2` は 44,988,023 回で **1.22 倍** だった。

追加・削除が重い用途では、この増加が効く。
右端ソートの共用なら、6 候補を維持したまま前処理を軽くできる。

### Hilbert 順序

集中した入力では移動回数が約 2044 万回から約 192 万回に減った。
一方、ランダムな区間では約 7316 万回から約 7840 万回に増えた。
測定した分布では、移動回数は変更前比 **0.094～1.45 倍** だった。

偏りの強い入力向けには有望。汎用の既定値としては、6 候補の方式が扱いやすい。

### 隣接交換

ランダムな区間で移動回数を **4.5 %**、短い区間で **18.0 %** 減らした。
交換は距離が縮む場合だけなので、総移動距離は増えない。
今回の軽い集計では、移動回数の削減がそのまま実時間の短縮には結びつかなかった。
Fenwick Tree などを更新する用途では、追加測定する価値がある。

### 初期位置を含めた評価

変更前の `mo_order_cost` はクエリ同士の距離だけを数える。
通常の `mo` では `(0,0)` から最初のクエリまでの距離も含めると、実際の移動回数で候補を選べる。

例：`{(52,79), (17,82), (29,49), (54,60)}` は、実移動回数が **194 → 182** になった。
大規模入力での効果は小さい。Slider 版では、その Slider の初期位置に合わせて評価する。

## 木上版に固有の改善

### `vector<bool>` と 1 バイト配列

処理順を固定し、前処理を除いた走査だけを各 7 回、順番を巡回させて追加測定した。
実時間とプロセス CPU 時間の両方を [mo_tree_walk.csv](mo_tree_walk.csv) に収録した。
以下は CPU 時間の中央値、単位は ms。実時間でも同じ傾向だった。

| 木・属性 | `vector<bool>` | `vector<unsigned char>` |
| --- | ---: | ---: |
| ランダム・頂点 | 403.2 | 437.6 |
| ランダム・辺 | 423.6 | 464.0 |
| 鎖・頂点 | 164.7 | 76.8 |
| 鎖・辺 | 162.5 | 94.1 |
| 星・頂点 | 206.1 | 198.1 |
| 星・辺 | 251.9 | 236.7 |

鎖では約 1.7～2.1 倍速いが、ランダムな木では約 9 % 遅くなった。
1 バイト配列は用途に応じて選ぶ候補とする。

### 追加・削除の分岐

種類数の更新を、現在の有無から決めた `+1/-1` で共通化する版も試した。
ランダムな木では速く、鎖・星では遅くなる場合があった。
集約処理に合わせた最適化であり、汎用の `add`・`del` を使う API への一律適用は慎重に判断する。

### LCA の計算

辺属性では `is_ancestor(u,v)` だけでオイラーツアー区間を決められる。
頂点属性でも、祖先と子孫のクエリは同じ判定で処理し、それ以外だけ LCA を求めればよい。
辺属性のクエリ変換は、最悪 $O(q\log n)$ から $O(q)$ になる。
処理順を決めるソートと走査の計算量は別にかかる。

## 検討時の推奨順

1. **右端のソートを共用する。** 6 候補を保ち、前処理を大きく短縮できる。
2. 最良候補だけを保持し、配列の繰り返し生成・コピーを減らす。
3. 大きい入力向けに、右端の基数ソートを検討する。小さい入力との切り替えは追加測定で決める。
4. 木上版は、祖先判定で済むクエリの LCA 計算を省く。

今回の適用では、移動距離の総和も `long long` に統一した。
変更前は座標型 `I` で足し合わせていたため、`I=int` では実行可能な入力でも総和が溢れ得た。
総和だけを広い型にし、木上版の区間座標は `int` にした。

```sh
g++-15 -std=c++20 -O2 -DNDEBUG -I . benchmark/mo.cpp -o /tmp/mo-bench
/tmp/mo-bench 100 200 1 check
/tmp/mo-bench 100 200 1
/tmp/mo-bench 200000 200000 5
/tmp/mo-bench 200000 1000 5 random
/tmp/mo-bench 20000 200000 5 random
/tmp/mo-bench 200000 200000 7 tree_walk
```

`mo.csv` は、配列 5 分布とクエリ数を変えた測定、および木 3 形状・2 属性の測定をまとめている。
測定後に追加した整列条件の検査は計測区間の外にある。
