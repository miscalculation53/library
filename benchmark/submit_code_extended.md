## 改善した箇所

`1'000'000'007` などの桁区切りを文字リテラルの開始と誤認し、後続する型・マクロへの
参照を見落としていた。そのため必要な宣言まで削除候補に入り、検証失敗と分割再試行が増えていた。
数値トークンを先に読み取る処理を、コメント除去・識別子抽出・構造解析などに共通して適用した。
16進数の `0xAB'CD`、小数・指数表記の桁区切りにも対応した。文字・文字列リテラルは内容を保つ。

- 多倍長整数の除算: コンパイラ起動 163 → 16 回、失敗 109 → 3 回。
- 任意 mod の畳み込み: コンパイラ起動 72 → 17 回、失敗 41 → 3 回。

他10入力のコンパイラ起動回数は同じだった。実行時間には揺れがあり、全入力が一様に高速化したという結果ではない。
削除候補を書き出す前のコンパイル・リンク確認と、制限内の中間結果を維持する処理は継続している。

## 検証

回帰テストは本体47件・バックグラウンド処理13件、計60件が成功した。追加した数値解析のテストは、
変更前の実装で失敗することも確認した。

元コード・最初の中間結果・最終結果、計36本を `-O2` でコンパイルし、
計225回の実行が別実装の期待値と一致した。配列の直接更新、素朴な多項式演算、
通常の行列消去、約数の列挙、グラフ探索などを期待値の計算に使った。多倍長整数は最大3,000桁を
Python の整数と比較し、畳み込みは変換処理に進む長さ、mod 2 行列は64ビット境界をまたぐサイズも含めた。

ポテンシャル付き UF の既存 verify は、`bool` の FAST_IO 出力が短縮前からコンパイルに失敗した。
この測定では、マージの成否を `int` に変換して出力する
[比較用入力](submit_code_potential.cpp) を使用した。既存の verify とライブラリ本体は変更していない。

## 再計測

変更前のツールを保存し、同じ出力ディレクトリを指定すると展開済み入力を再利用できる。

```sh
python3 -B benchmark/submit_code_matrix.py --output /tmp/cln-extended \
  --tool /tmp/submit_code_before.py --label before \
  --cases beats fps_composition bbla_rank dirichlet mod2 rectangles potential \
    inversions convolution_dynamic bigint aho connectivity
python3 -B benchmark/submit_code_matrix.py --output /tmp/cln-extended \
  --label after --cases beats fps_composition bbla_rank dirichlet mod2 rectangles \
    potential inversions convolution_dynamic bigint aho connectivity
python3 -B benchmark/submit_code_extended_check.py --output /tmp/cln-extended --label after
```

各コンパイラ起動の時間、入力・ツールのハッシュ、保存時点のサイズと時間は
[結果 JSON](submit_code_extended_results.json) に保存した。
