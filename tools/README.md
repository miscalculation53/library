# ツール

## 配置

実用ツールは直下に置き、Python と VS Code 拡張のテストは `tests/` にまとめる。
`compare_performance.py` は汎用の速度比較ツールとして公開し、個別の計測コードと結果はローカルで管理する。

## テスト

`requirements.txt` の依存を入れた Python 3.11.5 以上の環境と Node.js を使い、ライブラリのルートで実行する。
コンパイルを含むテストでは GNU C++ も使う。

`oj-verify` の四倍精度リンクには `.verify-helper/quadmath.specs` を使う。
GCC の既定のライブラリ指定を保ち、オブジェクトファイルの後へ `-lquadmath` を追加する。
これにより、Linux の `--as-needed` が有効な環境でも四倍精度関数をリンクできる。

```sh
python3 -m unittest discover -s tools/tests
node --test tools/tests/status.test.js
```

## 転置コードの生成

`transpose.py` は、線形な順方向の処理から転置を計算する C++ を生成する。
ループ・分岐・再帰と、既存の畳み込み・NTT・多項式の剰余を利用できる。
コンテストでの手順と `Do Use FFT` の解答例は
[転置コード生成](transpose_examples/README.md)を参照。
既存の C++ テンプレートから演算を記録して転置を構築する
[C++ 版](transpose_examples/CPP.md)も利用できる。

## `oj-verify` の互換モジュール

`online-judge-verify-helper==5.6.0` は、現在の `setuptools` から削除された
`pkg_resources.resource_string()` をドキュメント生成に使用しています。
`requirements.txt` は安全な最新版の `setuptools` を使いつつ `oj-verify` を保つため、
同じ処理を `importlib.resources` で行う最小互換モジュールを
`ojverify_pkg_resources_compat` からインストールします。

## GitHub Actions の verify 並列化

`.github/workflows/verify.yml` は、verify ファイルを10個の shard に分けて並列に
実行します。通常の8 shard には secret を渡さず、yukicoder 用の2 shard にだけ
`YUKICODER_TOKEN` を渡します。各 shard は timestamp、担当ファイル一覧、実際に
失敗したファイル、最後まで処理できなかったファイルを artifact に保存します。
`verify/atcoder/` は手動検証用として保存し、CI の実行・集約対象から外します。
AtCoder のシステムテスト取得に必要な `DROPBOX_TOKEN` は使用しません。
Pages では AtCoder のファイルを未検証の `❓` と表示します。
テストが失敗した場合も artifact のアップロードを試みます。各ジョブの Summary には、
担当した全ファイルを `Verified`、`Failed`、`Not completed` に分けて表示します。

テストデータの取得中に TLS 接続が途中で切れた場合は、該当ファイルだけを
5秒後・10秒後に最大2回再試行します。再試行も shard 全体の35分の制限に含めます。
再試行後も取得できなければ失敗として扱います。判定結果やコンパイルエラー、
証明書の検証エラーは通常どおり報告します。

`main` への push では、実際の verify 失敗がない場合に限り、全 shard の artifact が
CI 対象の全 verify ファイルを重複なく覆うことを `parallel_verify.py` で確認して timestamp を
統合します。その後にだけ `GITHUB_TOKEN` で timestamp を main へ反映します。
ドキュメント生成は verify の成否にかかわらず行い、実際に失敗したファイルを `❌`、
タイムアウト、キャンセル、artifact の欠落によって完了しなかったファイルを `❓` と
します。生成したJekyllサイトはGitHub公式のPages Actionsでビルドし、artifactとして
公開するため、`GH_PAT` は使用しません。mainを更新するジョブとドキュメントを公開する
ジョブは分かれており、前者だけに `contents: write`、Pagesのデプロイだけに
`pages: write` と `id-token: write` を与えます。pull requestではどちらの書き込み処理も
行いません。

Pages Actionsを初めて使うときだけ、GitHubの `Settings > Pages` で
`Build and deployment > Source` を `GitHub Actions` に変更する必要があります。

`parallel_verify.py` は workflow 内部用です。shard の選択はディレクトリ内の
verify ファイルを名前順に並べ、番号を shard 数で割った余りによって行います。
新しい verify ファイルも自動的にいずれかの shard へ入るため、通常はworkflowを
書き換える必要はありません。追加位置より後ろのファイルは所属shardがずれることが
ありますが、重複や漏れがないことはartifact統合時に検査します。
ディレクトリごとのshard数を変える場合や、新しいverifyカテゴリを追加する場合だけ
workflowの設定変更が必要です。

公開サイトの対象は `.verify-helper/docs/_config.yml` の `exclude` に従います。
除外対象のソースと Markdown は依存関係の収集前に外し、再生成時には既存の生成ページを
消してから作り直します。以前生成した開発用ページも、次回の公開対象から外れます。
生成 Markdown の本文にある `{{`・`{%` は、Jekyll の Liquid 構文として解釈される前に
文字列として出力する形へ変換します。C++ の初期化リストなどは元どおり表示し、
front matter とレイアウトの Liquid はそのまま扱います。
`oj-verify` が35分で全ファイルを処理できなかった場合、その shard は失敗ではなく
警告として終了し、未処理ファイルを Job Summary に表示します。GitHub Pages でも
未処理の verify ファイルは `❓` と表示し、実際に検証が失敗したものだけを `❌` と
して扱います。処理済みの timestamp と、未処理ファイルに以前の timestamp があれば
それを保持します。ジョブ自体がキャンセルされた場合や60分以内に終了できなかった
場合は、取得できた artifact を利用し、担当 artifact が存在しないファイルを `❓` と
してドキュメントを生成します。

GitHub の `ubuntu-latest` に `g++-15` がない場合は、標準搭載されている
`g++-14` を CI 内だけ `g++-15` という名前でも参照できるようにします。これにより、
手元の `.verify-helper/config.toml` を CI 用に書き換えずに利用できます。

`submit_code.py` は、コンテスト中に使う `main.cpp` にはライブラリをすべて
読み込める状態を保ち、提出用に生成する `bundle.cpp` だけを短くするツールです。

## コンテストディレクトリから使う

`main.cpp` があるディレクトリへ移動して、次のように実行します。

```sh
python3 "$HOME/library/tools/submit_code.py" \
  expand main.cpp -o bundle.cpp
```

カレントディレクトリは任意です。入力ファイルと出力ファイルは、カレント
ディレクトリからの相対パスまたは絶対パスで指定できます。

## 短縮コマンド

`aliases.zsh` を `.zshrc` から読み込むと、コンテストディレクトリでは次の
コマンドだけで実行できます。

```sh
source "$HOME/library/tools/aliases.zsh"
```

| コマンド | 処理 |
| --- | --- |
| `oj-b` | 従来と同様に `main.cpp` を高速に展開して `bundle.cpp` に出力する |
| `oj-bc` | `oj-b` の後に `cln` を続けて実行する |
| `oj-bs` | 展開後、安全確認付きで未使用ヘッダとコメントなどを除く |
| `oj-ba` | 展開後、未使用ヘッダに加えて未使用宣言も可能な範囲で除く |
| `cln` | 65,536 B 未満の中間結果を出し、その後も短縮を続ける |
| `cln-all` | サイズ制限用の中間結果を作らず、最終短縮だけを行う |
| `oj-b0` | `oj-b` の旧名として残している同じ処理 |

`oj-b` は通常のローカル `#include` を Python 内で直接たどります。ヘッダごとに
GNU C++ コンパイラを起動しないため、従来の `oj-bundle` より高速です。条件分岐内の
ローカル include など、高速展開器が扱わない書き方を検出した場合だけ、
`CXX=g++-15` 相当の設定で `oj-bundle` へフォールバックします。どちらの場合も
ローカルパスを含む `#line` は出力しません。展開した各ライブラリの先頭には、
GitHub の `wip` ブランチにある元ファイルへのリンクをコメントとして付けます。
外部ライブラリと提出元のファイルにはリンクを付けません。

提出元の `main.cpp` などに書いたコメントは、`cln` 後もできるだけ保持します。
行末コメントや複数行コメント、コメントアウトしたコードも保持の対象です。
ライブラリ内では、元ファイルへのリンクと `/*! ... */`・`//! ...` の重要コメントを保持します。
ライセンス・著作権・出典の表示には重要コメントを使います。
残るコードの重要コメントは元の位置を保ちます。展開で置き換える `#include` や
削除するガード行に付いた重要コメントは、その行の近くに残します。
削除したヘッダ・関数本体・無効な条件分岐内の重要コメントは、先頭へ移して保持する場合があります。
`f128` の環境判定（`__STDCPP_FLOAT128_T__` / `LIBRARY_HAS_FLOAT128` / `LIBRARY_USE_QUADMATH` を使う分岐）は保持し、提出先のコンパイラで四倍精度の実装を選び直します。手元でのリンク検証には常に `-lquadmath` を付けます。
同じ表示を移す際は重複を避け、本文をそのまま残します。
重要コメントに `@keep-if-code` と対象の識別子を指定すると、指定した名前が
コードからすべて消えた時点で、そのコメントも削除します。複数行で指定した名前は
まとめて扱い、1つでも残ればコメント全文を保持します。関数本体だけを削除して
宣言が残る場合や、マクロ定義に名前が残る場合も保持します。コメントや文字列内の
名前は判定から除きます。対象には、その表示が適用される関数・型・マクロなどの
名前をすべて、マクロ展開前のコードに現れる綴りで指定します。名前を結合する
マクロでは、そのマクロ名も指定します。指定を省略した重要コメントは従来どおり保持します。
ヘッダに指定を追加した場合は、`oj-b` で展開し直してから `cln` を実行します。
通常コメントは提出元のものを保持し、削除対象のコード内では一緒に消える場合があります。
サイズ判定には、保持したコメントのバイト数も含めます。

```cpp
/*! Copyright ...
 * @keep-if-code first_function second_type
 * ライセンスの条件・免責文を含む全文
 */
//! 参考: https://example.com/source
```

展開時のコメントは `.submit-code/出力ファイル名/comments.json` に記録します。
出力名を変えた場合や、展開後に元ソースを編集した場合も、この記録を使って短縮します。
既存の展開済みファイルでは、同じ場所の `main.cpp` または対応する元ソースから確認します。

通常は次の流れで使います。

```sh
cd "$HOME/contests/example"
oj-b
cln
```

上の2コマンドを続けて行う場合は、次の1コマンドで実行できます。

```sh
oj-bc
```

コード長に余裕があれば `oj-b` だけで構いません。`cln` は 65,536 B 未満の
検証済み候補ができた時点で `bundle.cpp` へ書き出し、その後も未使用宣言の削除を
続けます。`oj-bs` と `oj-ba` は候補を削除するたびにコンパイルとリンクを行うため、
通常の `oj-b` よりかなり時間がかかります。

ファイル名を変える場合は、入力、出力の順で指定できます。

```sh
oj-b a.cpp a-bundle.cpp
oj-bc a.cpp a-bundle.cpp
cln a-bundle.cpp
cln-all a-bundle.cpp
```

`oj-c`、`oj-s` などが内部で `oj-b` を呼ぶ既存の設定も、そのまま新しい
`oj-b` を使用します。

## 生成元を自動で照合する

元コードの SHA-256 の先頭12桁を、実行用ターミナル・VS Code の表示・生成ファイルの
最終行に共通のIDとして表示します。たとえば `#a1b2c3d4e5f6` のように照合できます。

生成ファイルの最終行には、完全な SHA-256 もコメントで記録します。

```cpp
// submit-code: hash=a1b2c3d4e5f6 source=... input=... body=...
```

`hash` は表示用ID、`source` は生成元の `main.cpp` など、`input` はローカルヘッダを
展開した内容、`body` は末尾の区切り空行と照合コメントを除く生成本文のハッシュです。
区切りの空行と照合コメントも提出用のバイト数に含めます。
参照したファイルのパスとハッシュは `.submit-code/出力名/comments.json` に保存します。

VS Code のローカル拡張は、保存済みのソースと生成ファイルを約0.5秒ごとに自動で照合します。
`main.cpp` または `bundle.cpp` を開くと、ステータスバーに「main.cpp と一致」または
「main.cpp と不一致」と表示します。編集中は直前のハッシュを維持し、保存時や実行前の
自動保存時に更新します。
一致時は共通ID、不一致時は元コードと生成側それぞれのIDを表示します。
表示に触れると完全な SHA-256 も確認できます。
参照ヘッダの変更や、生成本文を手で編集した場合も表示に反映します。
Code Runner／`oj-bg` の処理中は「bundle 中」「clean 中」を照合結果に併記します。
現在の出力に対応する短縮が終わると「clean 完了」と表示します。

手動の `oj-b`・`cln` と、Code Runner／`oj-bg` の生成のどちらにも対応します。
ハッシュ付きの生成ファイルだけでも元ソースと本文を照合でき、ヘッダの記録があれば
参照ヘッダも照合します。既存ファイルには、次回の生成から照合情報を追加します。
以前の1行目形式も照合でき、`cln` を実行すると末尾形式へ移行します。
生成本文を手で編集した後の `cln` は、その本文を短縮し、元の入力との照合情報を外します。

## Code Runner と並行して提出用コードを準備する

`submit_code_background.py start main.cpp` は、別プロセスで `oj-b` 相当の展開と
`cln` を順に実行し、開始したらすぐに戻ります。VS Code の
`code-runner.executorMap.cpp` で、従来のコンパイル・実行の前に呼び出せます。
`code-runner.saveFileBeforeRun: true` と組み合わせると、`Ctrl+Option+N` で保存した
コードを実行しながら、提出用コードも準備できます。

Code Runner では、普段のコンパイラ設定に合わせ、コンパイル・実行の直前に
このツールを呼び出します。実行は短縮完了を待ちません。
自動生成側は、環境が許せば優先度を下げて動作します。

C++ のコンパイル・起動は `run_cpp.py` を経由し、実行プログラムの起動時に
`[source hash] #a1b2c3d4e5f6` を標準エラーへ表示します。ID はコンパイル時に埋め込むため、
その後のソース変更や、同じ実行ファイルの再実行でも対応するIDを確認できます。
`Main<>` の初期化処理より先に表示するため、入力待ちの時点でIDを確認できます。
コンパイル中に元コードが変更された場合は再実行を促します。
`run_cpp.py` はコンパイル時に常に `-lquadmath` を付け、手元でも `f128` の数学関数と入出力を四倍精度で使えるようにします。既存の Code Runner の呼び出しにも適用されます。

`template_all.hpp` / `template_all_but_modint.hpp` を読むプログラムは、実行前にプリコンパイルを自動更新します。参照するヘッダの内容、コンパイラ、コンパイルオプション、テンプレートを読む前の `EPS` などの定義を記録します。同じ設定・参照ヘッダの組合せなら、別の問題のファイルや実行フォルダでも再利用します。定義の異なる設定も個別に保存するため、元の設定へ戻ったときも再利用できます。更新時は、キャッシュの初回作成や変更されたヘッダ名などの理由を表示します。

テンプレート前が単純な `#define`・`#undef`・条件分岐だけの場合は、コメントや空行の差を除いて比較します。`#include`、行継続、通常の C++ コード、`__FILE__` などを含む場合は、元の記述とソースの場所も記録します。参照ヘッダは毎回コンパイラで解決し、相対パスで異なるヘッダを読む場合や、新しいヘッダが追加された場合も対応するキャッシュを選びます。ヘッダの保存時刻だけが変わった場合や、問題を解く部分だけを編集した場合は再利用します。コンパイル中の変更検査には、その実行を始めた時点の内容と保存時刻を使います。

生成物は `template/.precompiled/` に保存します。従来のヘッダ隣の `.gch` は、最初の実行時に削除して管理対象のキャッシュへ移行します。プリコンパイルや本体のコンパイルに失敗した場合、または処理中に元コード・プリコンパイルの依存ヘッダが変わった場合は実行を止めます。

テンプレート変更後にプリコンパイルだけを更新する場合は、`--precompile-only` を付けます。Code Runner と同じオプションを渡すと、その設定のキャッシュを更新できます。

```sh
python3 tools/run_cpp.py --precompile-only template/template.cpp /tmp/template-check -- \
  g++-15 template/template.cpp -std=c++23 -DLOCAL \
  -I . -I ../cpp-dump-main -I ../../ac-library -o /tmp/template-check
```

```sh
python3 "$HOME/library/tools/run_cpp.py" \
  main.cpp exec -- g++-15 main.cpp -std=c++23 -o exec
```

- `main.cpp` の出力先は同じディレクトリの `bundle.cpp`。
- `a.cpp` など別名の入力は `a-bundle.cpp` に出力します。
- `bundle.cpp`、`*-bundle.cpp`、Code Runner の選択範囲用の一時ファイルは対象外です。
- 再実行すると、同じ出力先の古い生成処理とそのコンパイラを中止して最新のコードを処理します。
- 展開後の内容が同じなら、前回の中間結果から再開します。すでに完了していれば
  その結果を再利用します。ライブラリの変更も展開後の内容で検出します。
- 展開が完了した時点で `bundle.cpp` を最新の内容に更新し、その後 `cln` が確認した
  中間結果を順に反映します。短縮処理でエラーになった場合も、最後に出力した今回の
  内容が残ります。65,536 B 未満になった後も短縮を続けます。
  使用する機能によっては制限未満にならないこともあります。
- 元コードが保存し直された場合や出力が手動で変更された場合は、古い処理を中止します。
  展開の完了までは前回の出力が残るため、提出前には状態を確認してください。

進捗や失敗理由は、コンテストディレクトリで確認できます。

```sh
oj-bg-status       # 状態と今回の出力サイズを表示
oj-bg-stop         # 裏での生成を中止。最後の出力は残す
oj-bg             # コードの実行をせず、生成だけ開始
```

別名のソースは `oj-bg-status a.cpp` のように指定します。新しい短縮コマンドを
既存のターミナルで使うには、一度 `source "$HOME/library/tools/aliases.zsh"`
を実行します。Code Runner 側はこの読み込みを必要としません。
ログと制御用ファイルは `.submit-code/bundle.cpp/`（別名なら対応する出力名のディレクトリ）に
保存し、処理の詳細は `log.txt` に出力します。標準入力や実行中の端末には割り込みません。
自動生成は端末から独立しているので、端末を閉じても継続します。

### VS Code に照合結果を表示する

`vscode-submit-status/` のローカル拡張 **oj-b / cln 準備状況** は、VS Code 下部の
ステータスバーを約0.5秒ごとに更新します。コード実行用の端末やショートカットを
使わないため、表示中も `Ctrl+Option+N` で実行できます。

| 表示 | 状態 |
| --- | --- |
| `bundle 開始待ち` / `bundle 中` | 生成の開始待ち、またはインクルードを展開中。照合結果も併記 |
| `clean 中 \| main.cpp と一致 47,039 B \| #a1b2c3d4e5f6` | 現在の出力は元ソースと一致し、短縮も進行中 |
| `clean 完了 \| main.cpp と一致 47,039 B \| #a1b2c3d4e5f6` | 現在の出力に対応する短縮が完了 |
| `main.cpp と一致 47,039 B \| #a1b2c3d4e5f6` | 現在の元ソースと生成元が一致し、生成本文も一致 |
| `main.cpp と不一致` | 現在の元ソースと生成時の内容が異なる |
| `ヘッダに変更あり` | 参照ヘッダが生成時から変更されている |
| `生成本文に変更あり` | 生成ファイルの編集内容が保存されている |
| `照合情報なし` / `未生成` | 次回の生成で照合可能になる |
| `編集により中断` | 元コードや提出用ファイルの編集を検知して中断。次の実行で再生成 |
| `生成エラー` / `停止` | 生成の失敗または停止。最後の出力との照合結果も併記 |

表示は現在開いている C++ ソースに対応します。生成済みの `bundle.cpp` を開いた場合は
元のソースを参照します。端末やログへ移動しても、直前の対象の表示を維持します。
クリックすると「出力」パネルに生成ログを開き、自動更新します。エディタのフォーカスは
移しません。コマンドパレットの `oj-b / cln: 提出用コードを開く` から出力を開けます。

編集中も、裏の生成は最後に保存したソースを対象に進みます。ソースを保存して内容が
変わると古い生成処理は中止し、次の `Ctrl+Option+N` で最新コードから再生成します。
拡張は元ソース・生成本文・参照ヘッダの保存済みの内容を照合します。編集中は直前の
ハッシュを保ち、保存や実行、外部ツールによる生成結果の更新を表示に反映します。
65,536 B 以上の場合は、表示に触れるとサイズ制限も確認できます。

拡張はローカルの状態ファイルを読むだけで、コンパイラを追加で起動しません。
インストール用ファイルは次のように作成できます。外部パッケージや公開操作は不要です。

```sh
node --test tools/tests/status.test.js
python3 tools/vscode-submit-status/package.py /tmp/kyopro-submit-status-0.3.2.vsix
```

VS Code の「VSIX からのインストール」で生成したファイルを選択します。
インストール直後に表示されない場合は、C++ ファイルを開き直してください。

## 高速な展開

```sh
python3 tools/submit_code.py expand main.cpp -o bundle.cpp
```

`#pragma once` または一般的な include guard の付いたローカルヘッダを読み込み、
重複を除きながら展開します。対応していない include の形では自動的に
`oj-bundle` を使います。フォールバックを禁止して検査したい場合は
`--no-fallback` を指定します。

## 安全確認付きの展開

```sh
python3 tools/submit_code.py bundle main.cpp -o bundle.cpp
```

次の処理を順に行います。

1. リポジトリのインクルードパスを指定して `oj-bundle` を実行する。
2. ローカルパスを含むすべての `#line` を `bundle/...` という仮想パスに置き換える。
3. 展開されたヘッダを単位として、削除後もコンパイルとリンクが通る未使用部分を除く。
4. 重要コメント・提出元のコメント・元コードへのリンクを保持し、その他のコメントと無効な
   プリプロセッサ分岐を除き、連続する空行を1行にまとめる。
5. 最終出力から `#line` を除く。

短縮が受理されるたびに、コンパイルとリンクが通る状態をアトミックに
`bundle.cpp` へ書き出します。途中で停止しても、最後に確認できた状態が残ります。

主なオプションは次の通りです。

```sh
# 個人情報を含まない仮想パスに直した #line を残す。
python3 tools/submit_code.py bundle main.cpp --keep-line

# 宣言単位の未使用コード削除も行う。
python3 tools/submit_code.py bundle main.cpp --aggressive

# 先の削除で依存関係が変わった場合を考慮し、ヘッダ削除を再試行する。
python3 tools/submit_code.py bundle main.cpp --header-passes 2

# インクルードパスやコンパイラオプションを追加する。
python3 tools/submit_code.py bundle main.cpp -I path/to/library \
  --cxx-arg=-DMOD=998244353
```

`g++-15`、`g++-14`、`oj-bundle`、リポジトリ内の
`.venv/bin/oj-bundle` は自動的に探索します。明示的に指定する場合は
`--cxx` または `--oj-bundle` を使います。

検証時には `<bits/stdc++.h>` のプリコンパイル済みヘッダを再利用します。
`<bits/stdc++.h>` より前に定義した設定用マクロもキャッシュへ含めるため、通常の
テンプレートをそのまま展開した `bundle.cpp` でも利用できます。初めて現れた
設定ではキャッシュ生成に時間がかかりますが、同じ設定の次回以降は再利用します。
ただし、コメント整理や未参照の型などの削除でサイズ制限を満たす最初の候補は、既存キャッシュだけを
利用し、新規生成を待ちません。新しいキャッシュは、その後の繰り返し検証で
必要になった時点で作成します。
キャッシュ先は `$SUBMIT_CODE_CACHE_DIR`、未指定の場合はシステムの一時
ディレクトリです。コンパイラ、C++ 規格、インクルードパス、コンパイラ
オプションが異なる場合は別のキャッシュを使用します。

## 既存ファイルの短縮

`cleanup` は、すでにある `bundle.cpp` をその場で短くします。既定では
65,536 B 未満になった最初の候補をすぐ書き出し、その後も短縮を続けます。

```sh
python3 tools/submit_code.py cleanup bundle.cpp
```

C++23 を既定値とし、次の順に処理します。

1. 既に 65,536 B 未満なら、そのファイルを提出可能な中間結果として維持する。
2. インデントと行内の空白、重要コメント・提出元のコメント・元コードへのリンクを保ち、
   その他のコメントを除く。連続する空行を1行にまとめて構文を確認する。
3. 65,536 B 未満なら、その候補をアトミックに書き出す。
4. 無効な分岐を除き、ここで制限を満たした候補も構文確認後に書き出す。
5. 型・型エイリアス・キャプチャのない `constexpr` ラムダ間の参照をたどり、
   外部から参照されないまとまりを探す。これで制限を満たせる場合は、先に
   コンパイルとリンクを確認して書き出す。自分のコンストラクタや型エイリアスから
   参照されるだけの未使用型も対象になる。
6. GCCのテンプレート解析を行い、実体化されなかった関数やメソッドの本体と不要な宣言を削除する。
   候補の抽出には構文解析までの結果を使い、この段階の実行用コード生成を省く。
   制限に達する前は、名前が宣言箇所にしか現れない候補の宣言も本体と一緒に
   削除し、コンパイルとリンクが通れば直ちに書き出す。失敗した場合は宣言を
   残す方法に戻す。
   ラムダが内部に生成する呼び出し演算子は通常の関数として削除せず、宣言の
   削除時には `requires` 節や属性も含める。
   必要な定義が見つかった場合は、そこから参照されるテンプレート候補も
   まとめて残し、依存先を一つずつ確認する再コンパイルを減らす。
   まとめて残すと残りのテンプレート候補をすべて削っても制限を満たせない場合は、
   コンパイラの診断で必要な定義を一つずつ確かめる。
7. 短縮後のコードを無名名前空間化し、コンパイラに加えて `cppcheck` も使い、既定では最大3周解析する。
   `namespace std` のブロックは元の位置に保ち、その前後を無名名前空間にする。
   標準ライブラリの特殊化を含むライブラリでも未使用関数を検出できるようにする。
   各周で、ほかの削除により外部から参照されなくなった型なども再び調べる。
8. 最後にGCCのIPA解析を行い、外部から到達しない関数群を削除する。

型などの参照解析では、同じ名前を別スコープで使っている場合は保守的に残す。
オブジェクトを同時に定義する構造体、初期化処理を伴い得る静的メンバ、
`friend` 宣言、キャプチャや即時呼び出しのあるラムダも、この方法では削除しない。
宣言を削る候補は、構文だけでなくリンクまで通った場合に書き出す。
数値の桁区切り（`1'000'000'007`、`0xAB'CD` など）は文字リテラルと区別し、
その後にある型・マクロ・関数への参照も解析する。

中間結果を書き出した後も処理は続きますが、ディスク上の `bundle.cpp` が再び
65,536 B 以上の候補で上書きされることはありません。サイズ制限用の中間結果を
作らず、最終的な短縮だけを行うには、`cln-all` または次を使います。

```sh
python3 tools/submit_code.py cleanup bundle.cpp --target-bytes 0
```

別の制限を指定する場合、たとえば 100,000 B 未満なら次のようにします。

```sh
python3 tools/submit_code.py cleanup bundle.cpp --target-bytes 100000
```

コメントなどだけを高速に除き、宣言単位の解析を行わない場合は次を使います。

```sh
python3 tools/submit_code.py cleanup bundle.cpp --safe-only
```

どちらの処理も、解析、検証、書き出しの各段階と所要時間、変更前後のバイト数を
表示します。端末では段階ごとに自動で色が付き、バイト数は太字で強調されます。
色を明示的に無効化するには
`--color never`、端末以外への出力でも有効化するには `--color always` を指定します。
削除したヘッダや宣言を表示するには `-v` を指定します。

直接 `#include` したローカルヘッダは常に残します。推移的に読み込まれた
ヘッダと未使用宣言は、削除後にコンパイルとリンクが通った場合だけ除きます。
グローバルな副作用があるため残したいヘッダは、たとえば
`--keep-header 'bundle/include-0/path/to/header.hpp'` のように指定できます。
